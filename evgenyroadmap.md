# Evgeny Roadmap — доделать и починить SuperAgents OS

> Дата: 2026-09-09. Статус: план, кода нет. Источник — 10 пунктов от Evgeny.
> Принципы: постепенно, узкими batch (1 задача → проверка → STOP), без архитектурного раздувания, runtime-верификация после каждого batch.

## Карта треков

| Трек | Пункты | Суть |
|------|--------|------|
| T0 Фундамент | 9, 8 | Инвентаризация сервисов + разобраться с Fleet-панелями |
| T1 Ротация | 6, 3, 4 | SSOT ротации → панель ротации → привязка агента к ключу/модели |
| T2 Чаты | 2 | Выбор ключа + модели: глобальный дефолт + override на чат |
| T3 Агенты-учёные | 1, 5, 7 | RU-роли (химик, математик…), сиды, карточка агента с действиями |
| T4 Исследование | 10 | OpenCode — только research, решение позже |

Порядок — T0 → T1 → T2 → T3 → T4 (каждый этап независимый релиз, можно переставлять).

## T0. Фундамент: понять, что уже есть

### Этап 0.1 — Инвентаризация сервисов (п.9)
**Зачем:** половина вопросов («что за сервисы мы написали») снимается одним документом.
**Что сделать:**
1. Пройти `src/kernel/services/` + `src/kernel/service-registration/phase*.ts`, выписать каждый сервис: назначение, DI-имя, зависимости, потребляющие панели.
2. Отдельно выписать: keyService / provider-adapter-registry / router / rate-limit / priority-queue / circuit-breaker (это и есть текущая «ротация»), debate-runtime путь, role/agent сервисы, chat store.
3. Результат: `docs/SERVICES_INVENTORY.md` — таблица + схема зависимостей.
**Критерий готовности:** по любому сервису можно за 1 минуту ответить «зачем он и кто его зовёт».
**Не делать:** рефакторинг, переименования, удаления.

### Этап 0.2 — Fleet-панели и «новые панели» (п.8)
**Зачем:** понять, какие панели что показывают, прежде чем добавлять новые (п.6, п.7).

**Критерий готовности:** список «панель → данные → действия», помечены dead/дубли.

## T1. Ротация ключей и привязки (п.6, п.3, п.4)

### Этап 1.1 — SSOT ротации: описать текущую механику (п.6, часть 1)
**Что известно сейчас:** ключи — `keyService` + `key-models.ts` (списки моделей на провайдера), вызовы идут через декораторы `rate-limit → retry → circuit-breaker → priority-queue → cost → cache → logging`, дефолтные модели — `provider-default-models.ts` (+ копии в `probe-service`, `debate-query-engine`, `role-team-service`, `config-registry` — уже правились под Llama 4).
**Что сделать:**
1. Описать фактическую цепочку выбора «ключ + модель» для трёх путей: debate (`debate-query-engine: pickBestModelForDebate`), teams (`role-team-service: pickProviderAndKey`), чаты (уточнить в коде на этапе).
2. Зафиксировать, где ротация random, где priority, где circuit-breaker скипает.
3. Результат: `docs/ROTATION.md`.
**Критерий готовности:** документ отвечает «как Шас сейчас выбирает ключ для агента/дебатов».

### Этап 1.2 — Панель ротации: вид + настройка (п.6, часть 2)
**Что сделать:**
1. Новая панель (или вкладка существующей Keys-панели — решить на этапе после T0): таблица «провайдер → ключи → статус/circuit → модели», текущие дефолты из SSOT.
2. Настройки: порядок провайдеров для дебатов, exclude-список моделей (типа мёртвых llama-3.x), лимиты.
3. Хранение настроек — через существующий config/keyValue, без новых таблиц.
**Критерий готовности:** в UI видно, как настроена ротация, и её можно поменять без кода.
**Не делать:** переписывание самого движка ротации.

### Этап 1.3 — Привязка агента к ключу/модели: создание (п.3)
**Что сделать:**
1. В форме создания агента: переключатель «Ротация (по умолчанию)» / «Фиксированный ключ + модель».
2. При фиксированном — селекты ключа (из `keyService.getKeys()`) и модели (из `key-models.ts` списка провайдера ключа).
3. Хранение: поля на агенте (уточнить модель агента на этапе), runtime — `pickBestModel`-пути сначала смотрят override, иначе ротация.
**Критерий готовности:** созданный с привязкой агент всегда ходит через свой ключ/модель; с ротацией — как раньше.

### Этап 1.4 — Привязка агента к ключу/модели: редактирование (п.4)
То же, что 1.3, но в форме редактирования + миграция старых агентов (у всех — «Ротация»).
**Критерий готовности:** старый агент после открытия формы показывает «Ротация», можно переключить и сохранить.

## T2. Чаты: ключ + модель (п.2)

### Этап 2.1 — Глобальный дефолт
Настройки (существующий settings/config): дефолтные key + model для новых чатов. Сейчас дефолты разбросаны (`config-registry`, `chat-panel-utils`, stores) — свести к SSOT.

### Этап 2.2 — Override на чат-сессию
В шапке/настройках чата: селекты ключа и модели, по умолчанию «как в глобальных». Хранение — поля на чат-сессии. Отправка сообщения использует override → fallback на глобальный дефолт.
**Критерий готовности:** два чата одновременно ходят через разные ключи/модели; новый чат берёт глобальный дефолт.

## T3. Агенты-учёные RU + карточка (п.1, п.5, п.7)

### Этап 3.1 — Пакет RU-ролей учёных (п.1, п.5)
**Что сделать:**
1. Seed-пакет ролей на русском: химик, математик, физик, биолог, историк, экономист, программист/инженер, врач, юрист, философ (+ какие скажешь — список фиксируем перед batch).
2. У каждой: имя, описание RU, systemPrompt RU, категория, иконка/цвет, рекомендованная температура.
3. Куда класть: новый seed-файл (старый `data/*` в репо отсутствует — восстановить как `src/data/` + обновить fallback-заглушки в `debate-archetypes`, `debate-historical-figures`, `PersonaPickerPanel`, `RoleLibrary`, `role-team-service`, `unified-role-service`).
**Критерий готовности:** роли видны в библиотеке/пикере, устанавливаются в один клик, говорят по-русски.
**Вопрос к тебе перед batch:** точный список ролей (10–15) и нужны ли persona-персоны (конкретные учёные: Менделеев, Лобачевский…) или только ролевые архетипы.

### Этап 3.2 — Карточка агента: профиль + действия (п.7)
**Что сделать:** отдельный вид агента: характеристики (имя, описание, systemPrompt, температура, категория), привязка ключ/модель (из T1, read + shortcut в редактор), статистика (вызовы, успех, токены — что уже считает система), история/последние выполнения, действия: «Тест» (пробный вызов), «Дублировать», «В дебаты», «Редактировать», «Удалить».
**Критерий готовности:** агента можно открыть отдельно, всё видно, действия работают.
**Не делать:** новую систему статистики — только то, что уже собирается.

## Правила выполнения (для Шас)
1. Один этап — один узкий batch → проверка (typecheck + vite boot + ручной smoke по критерию) → STOP.
2. Каждый batch: что меняем, evidence (файл:строка), что НЕ трогаем.
3. Никаких новых таблиц Dexie без необходимости; настройки — в существующие config/keyValue.
4. Regression: если batch чинит поведение — минимальный тест рядом.
5. Порядок этапов можно менять, но T1.3/T1.4 — только после T1.1 (надо знать механику), T3.2 — после T1 (привязка должна существовать).
