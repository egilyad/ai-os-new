## Назначение

Противоречия/дубли/устаревшие знания; источники и доверие; цитируемость; можно ли к выводу задать «почему» и получить цепочку.

## Методология

Контент-анализ Wiki/графа + карты: Knowledge Quality, Decision Provenance, Source Quality/Citations, Contradiction.

## Что уже есть (факты из аудитов)

- W2-014: дебаты не сохраняют provenance «какие memories повлияли на вывод» (debate→memory link отсутствует; grep `debateMemory|memoryUsedIn` = 0).
- W8-012/015: retrieval — O(N)-скан, recall перезаписывает `lastAccessedAt` на каждый вызов; `VectorSpace.match` O(NxD).
- W7-ANA-013: аналитика фабрикует «ежедневные тренды» из lifetime-сумм (W6-003 — percentiles в UI исправлены, показывают «—» без данных).
- W3-006: exportToJson/importFromJson покрывает 16/136 доменов → знания не полностью восстанавливаемы.
- W8-013: SemanticMemoryStore и соседние store — cap+sort-per-write, in-memory, без устойчивости.
- Knowledge-граф: источники/связи есть, но «почему так решил агент» не воспроизводится (по provenance).

## Пробелы / риски

- Нет всейпочему?»-цепочки: источник → аргументы → решение/вывод.
- Противоречивые/дублирующиеся знания не детектируются автоматически.
- Retriesal без индекса/покрытия; результат зависит от хэша и порядка.
- Устаревшие записи не имеют TTL/архивации; источник не связывается с датой/уверенностью.
- Синтез/дебаты не оставляют верифицируемого следа для пересмотра.

## Рекомендации

1. Ввести provenance-слой: для каждого вывода хранить цепочку источников/агентов/версий промпта.
2. Авто-детекция противоречий и дублей в Wiki/графе.
3. Построить индекс для recall (вместо O(N)-скан) с TTL.
4. Обязательные поля для знаний: источник + дата + степень доверия.
5. Пересматривать старые выводы при опровержении источника.
