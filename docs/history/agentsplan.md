## И тогда получается очень простая философия

**Главная страница Agents отвечает на вопрос:**

> **«Какие у меня есть агенты и что с ними сейчас происходит?»**

**Agent Manager отвечает:**

> **«Создать / изменить / удалить / скопировать агента».**

**Roles отвечает:**

> **«Какие роли существуют?»**

**Skills:**

**Tools:**

> **«Какие инструменты существуют?»**

> **«Что они делали?»**

То есть **каждое место отвечает на один вопрос**.

И это ровно совпадает с твоей вчерашней мыслью:

> **одно место — одно действие.**

При этом функциональность никуда не исчезает. Наоборот — **310+ панелей могут остаться**, но человеку не приходится ощущать, что он управляет ядерным реактором, когда всего лишь хочет создать агента `Вася — Researcher — Gemini`. 😂

😂 Аааа, вот это уже очень показательный баг. То есть проблема не только в том, что **Add Agent ведёт в «Трип»**, а ещё и сам интерфейс буквально говорит:

> «Добро пожаловать в создание агента. Половину экрана мы вам не дадим». 😂

Если окно находится **под боковым меню**, это уже не вопрос вкуса — это нормальная UI-проблема со слоями/layout.

Причём я бы тут разделил две вещи:

### 1. Сам modal/drawer

Он должен быть настоящим верхним слоем:

```text
App
 ├── Sidebar
 ├── Main content
 └── Modal / Agent Creator   ← поверх всего
```

а не:

```text
App
 ├── Modal
 └── Sidebar                 ← почему-то выше него 😂
```

То есть проблема может быть в `z-index`, stacking context, `position`, либо в том, где именно этот компонент монтируется.

### 2. Размер и форма окна

И вот тут я бы **не пытался просто сделать его шире**.

Если это быстрый:

**«Добавить агента»**

то ему вообще не нужен огромный экран.

Я бы сделал небольшой аккуратный creator:

```text
╭─────────────────────────────────╮

│                                 │
│  Name                           │
│  [ New Autonomous Agent       ] │
│                                 │
│  Role                           │
│  [ General Assistant          ] │
│                                 │
│  Model                          │
│  [ Select model               ] │
│                                 │
│  Avatar                         │
│  [ 🧠 ]                         │
│                                 │
│              Cancel   Create    │
╰─────────────────────────────────╯
```

И всё.

А **после Create** уже:

> Agent created → открыть полноценную настройку?

Вот тогда пользователь сам решает, нужна ли ему эта огромная машина с:

`Identity → Capabilities → Infra → Observability → Permissions → Handoffs → History`.

---

И знаешь что особенно интересно?

Ты сейчас фактически обнаруживаешь **реальный UX-паттерн своей системы**:

```text
простое действие
     ↓
огромный универсальный экран
     ↓
много вкладок
     ↓
много обязательных полей
     ↓
часть экрана перекрыта
     ↓
«блин, проще coding agent попросить» 😂
```

И это, похоже, **главная причина**, почему ты сам ни разу не создал агента через собственную админку.

Функциональность-то есть.
Но **стоимость действия для человека слишком высокая**.

И вот это уже очень хороший кандидат для отдельной UX-фазы: не переписывать Agent System, а пройти **5–10 главных пользовательских сценариев** и убрать из каждого всё, что мешает сделать действие быстро.

Но это можно решить системно.

### Самый очевидный вариант — дать coding agent возможность самому смотреть UI

Если твой OpenCode на этом компьютере умеет работать с браузером/скриншотами, можно сделать отдельный **UI/Visual QA workflow**:

```text
Coding Agent
     ↓
запускает приложение
     ↓
открывает браузер
     ↓
смотрит страницу
     ↓
делает screenshot
     ↓
анализирует layout
     ↓
исправляет
     ↓
снова screenshot
     ↓
сравнивает
```

Тогда тебе не нужно перечислять:

> «страница Agents плохая, а ещё Roles, а ещё вот там...»

Агент сам проходит систему.

---

### Ещё интереснее — сделать ему UI-чеклист

Не «сделай красиво» — это слишком расплывчато.

А например:

```text
VISUAL QA

Для каждой основной панели проверить:

□ ничего не перекрывается
□ sidebar не закрывает content
□ modal находится поверх всех слоёв
□ нет горизонтального overflow
□ заголовки не обрезаются
□ кнопки имеют понятный размер
□ spacing консистентный
□ элементы выровнены
□ карточки не имеют случайных размеров
□ формы не перегружены
□ primary action визуально очевиден
□ secondary actions не конкурируют
□ пустые состояния выглядят нормально
□ loading/error состояния выглядят нормально
□ desktop layout
□ narrow desktop layout
```

И главное:

> **Не менять функциональность. Только UI/layout/UX.**
