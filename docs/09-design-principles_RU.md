# 09 — Принципы проектирования

## Концептуальный уровень

Система руководствуется набором архитектурных принципов, которые ограничивают способы создания функций и взаимодействия компонентов. Эти принципы существуют потому, что предметная область (многоагентное LLM-рассуждение) по своей природе ненадёжна — LLM генерируют неструктурированный, невоспроизводимый вывод, и архитектура должна это компенсировать.

## Принципы

### 1. Никакого единого источника истины в выводе LLM

Вывод LLM никогда не считается единственным источником истины для каких-либо структурных решений. Весь текст, сгенерированный LLM, парсится, валидируется и дополняется резервной логикой:

- Теги `[parent:xxx]` в аргументах имеют 4-уровневый резервный механизм разрешения (явный → fallback_latest → сирота → invalid_reference)
- Уверенность вычисляется эвристически на основе текстовых признаков, а не с помощью LLM
- Соблюдение ограничений оценивается через регулярные выражения/сопоставление с шаблонами, а не суждением LLM
- Интерпретатор вообще не использует LLM — все выводы основаны на структуре

### 2. Всё измеримо

Каждые дебаты порождают количественные метрики. Нет ни одной функции, которая выдаёт неструктурированный вывод без соответствующих измерений:

- Аргументы → графовые метрики (глубина, ветвление, доля сирот)
- Агенты → метрики активности (количество, уверенность, ответы)
- Контент → метрики качества (глубина, оригинальность, полезность)
- Утверждения → оценка конвергенции, плотность противоречий

### 3. Резерв существует всегда

Каждая операция, которая может завершиться ошибкой, имеет резервный вариант:

- Вызовы LLM: 4-уровневый резерв провайдеров (тот же ключ → тот же провайдер → кросс-провайдер → запасной аргумент)
- Разрешение родителя: 4-уровневый (явный → недавний → сирота → неверный)
- Маршрутизация провайдеров: циклический перебор активных ключей на провайдер
- Разрешение модели: значения по умолчанию для конкретного провайдера, когда `modelId` не определён
- Консенсус: резерв на синтез текста, если путь губернатора не сработал

### 4. Структура надёжнее текста

Структурированные данные предпочтительнее необработанного текста для всех процессов принятия решений:

- `DebateArgument` — типизированный объект, а не строка
- Граф утверждений — это DAG с типизированными рёбрами (поддерживает/оспаривает/уточняет)
- `ParentResolution` — это перечисление, а не поле со свободным текстом
- Метрики числовые, а не описательные
- События имеют типизированные полезные нагрузки, валидируемые схемами Zod

### 5. Интерпретация отделена от генерации

Уровень генерации создаёт текст. Уровень интерпретации читает структурированные данные. Они никогда не смешиваются:

- `DebateService` генерирует аргументы через `callLLM()`
- `DebateInterpreter` читает массив аргументов и граф утверждений — без вызовов LLM
- Интерпретатор не может вводить новые утверждения или галлюцинировать рассуждения
- Это разделение гарантирует, что интерпретация детерминирована и воспроизводима

### 6. Мутации атомарны с согласованностью в конечном счёте

Система использует паттерн «Граница транзакции»:

- Все методы мутации принимают опциональный `tx?: ITransaction`
- С tx: персистентность и отправка событий откладываются до момента фиксации
- Без tx: немедленная отправка и персистентность
- Откат отбрасывает все ожидающие операции
- Это позволяет выполнять атомарные множественные мутации (например, `setSLAMode` + `setBaseWeights` в одной транзакции)

### 7. Ядро никогда не зависит от UI

Направление зависимостей строго однонаправленное: UI → Приложение → Ядро → Инфраструктура. Код ядра не импортирует ничего из React, DOM или любых UI-библиотек. Вся коммуникация от ядра к UI проходит через EventBus.

### 8. Состояние иммутабельно с точки зрения потребителя

`getState()` возвращает `deepFreeze(structuredClone(state))` — потребители не могут мутировать состояние ядра. Все мутации проходят через явные методы (`setSLAMode`, `setBaseWeights` и т.д.).
