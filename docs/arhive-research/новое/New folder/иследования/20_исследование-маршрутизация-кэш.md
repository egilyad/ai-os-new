# Исследование: Маршрутизация LLM, fallback и семантический кэш

## 1. LLM Router (три парадигмы)

- Классификатор сложности/качества (RouteLLM: mf/bert/sw_ranking; Semantic Router): предсказывает win-rate сильной модели → порог.
- Семантический (Aurelio Semantic Router, CanaryRouter): эмбеддинг → ближайший маршрут.
- Эвристический/балансировка (LiteLLM gateway, OpenRouter, Portkey): стоимость/латентность/health.

RouteLLM (arXiv 2406.18665): win-rate сильной модели + cost threshold; роутеры mf (рекоменд.)/sw_ranking/bert/causal_llm; результат: до −85% стоимости при 95% качества GPT-4 на MT-Bench. Калибровка порога по проценту запросов в сильную модель.

Semantic Router (Aurelio): IndexedRouter (эмбеддинг → маршрут), DecisionRouter (маленькая decision-модель); калибровка fit(X,y)→confidence_threshold (порог 0.5 осмыслен); Chain (быстрый сначала, медленный при неуверенности); Merge (усреднение); гибрид sparse+dense.
NotDiamond: тренировка роутера под домен.

## 2. Семантический кэш

GPTCache (эталон): компоненты — эмбеддинг, векторный стор, хранилище ответов, similarity-оценщик (расстояние/dup-классификатор/exact/BM25). Exact почти бесполезен; similar поднимает hit-rate. Метрики: Hit Ratio, Latency, Recall, false positives/negatives. Порог — компромисс; пропускать при temperature>0 (стохастика). Eviction LRU/FIFO/LFU.
Redis semantic caching: эмбеддинг → vector similarity (HNSW) → порог.

## 3. Fallback / circuit breaker в гейтвеях

LiteLLM: три типа fallback (fallbacks для 429/500; context_window_fallbacks → модель с большим окном; content_policy_fallbacks → другой провайдер); num_retries (fixed+exponential backoff); circuit breaker/cooldown (allowed_fails:3 → cooldown 30s); маршрутизация по деплойментам (simple-shuffle рекомендуется, latency-based, usage-based не рекомендуется, cost-based); pre_call_checks (отфильтровать кандидатов по max_input_tokens/региону/vision); traffic mirroring (silent A/B); spend/fallback-логи (attempted_fallbacks, original_model_group).
Portkey/Helicone: edge-шлюзы, fallback, guardrails. Langfuse: observability, LLM-as-judge, prompt-менеджмент.

## 4. Оценка качества маршрутизации

1. Стоимость ($/запрос, % экономии против «всё в сильной»).
2. Латентность (p50/p95/p99 + накладные роутера/кэша).
3. Качество: оффлайн бенчмарки + LLM-as-judge + traffic mirroring.
4. Trade-off: сильная-модель call rate при фиксированном качестве (Pareto-кривая).
5. Кэш: hit-rate, recall, latency, false-positive rate.
6. Надёжность: % успешных без fallback, % с fallback, среднее число попыток, cooldown-события.

## Рекомендации для нашего приложения (13 декораторов, UCB1, SemanticRouter/CanaryRouter/CompressRoute)

1. Собрать управляющий слой (gateway-оркестратор), который реально вызывает написанные роутеры (сейчас мёртвый код).
2. Порядок исполнения:
   - семантический кэш первым (эмбеддинги, порог по false-positive rate);
   - SemanticRouter → намерение/маршрут + fast→slow (Chain), UCB1 решает «покупать» ли дорогую модель (exploration/exploitation);
   - Fallback/circuit breaker по классам ошибок (LiteLLM-паттерн), cooldown, retry+backoff, деградация на дешёвую модель;
   - CompressRoute перед передачей в LLM.
3. Калибровка вместо эвристик: SemanticRouter fit()+confidence_threshold; UCB1/порог сильной модели — на датасете нашего трафика (RouteLLM calibrate_threshold).
4. Оценка: traffic mirroring на сильную модель; трейсить решения; логировать attempted_fallbacks/original_model_group; считать экономию/hit-rate/false-positive/fallback-долю/сильная-модель call rate.
5. Гигиена декораторов: каждый измерим; запускать только подключённые под флагом.
