## Зачем это

Большой проект, написанный с помощью ИИ, даёт «бесконечную очередь багов»: аудит находит сотни, ты чинишь, следующий аудит находит новые. Это не значит, что ты делаешь плохо — это особенность больших сложных систем. Цель этого учебника — дать методологию, как сделать аудиты управляемыми и конечными.<|think_end|>---

## Почему баги не кончаются

1. **Сложность системы.** Чем больше модулей и связей, тем больше «краёв», где живут баги.
2. **Исправления меняют систему.** Каждый фикс меняет поведение и может открыть новые углы.
3. **Пере охват аудита.** Один аудит не видит всё: он работает в одной «проекции» (память, безопасность, данные, гонки, контракты).
4. **Разрастающаяся зона риска.** Быстро растущая ИИ-база сама плодит новые области риска.

Вывод: **поймать все баги сразу — невозможно.** Можно стабилизировать систему по частям.

## Цель аудита

Сменить цель с «найди все баги» на «стабилизируй конкретную зону»:

- один аудит = одна проекция (память или безопасность, а не «всё»);
- приоритет строго по серьёзности: CRITICAL/HIGH → тест/чек-кейс на каждый;
- после фикса — регрессионная проверка зоны.

## Уровни стабильности и freeze

- **Freeze:** на время стабилизации не добавляем новый функционал.
- **Уровни A/B/C:** модули делим на стабильные (A), рабочие но рискованные (B), экспериментальные (C). Аудиты гоняем по A и B; C — изолированно.
- **Ядро:** сначала стабилизируем минимальный happy-path, затем расширяем зону.

## Целевые промты вместо общих

Общий промт «найди баги» даёт хаос. Точный промт направляет аудит в одну проекцию: «найди утечки памяти», «проверь авторизацию и песочницу» и т.д. Так результаты предсказуемее и ближе к «полной картине» по конкретной зоне.

## Пять готовых промтов

Ниже — готовые узкие промты (из исходного файла), которые можно копировать и запускать через агента.

### 1. Memory / resource leaks

```text
Аудит: утечки памяти и ресурсов. Найди места, где создаются и не освобождаются listener/таймеры/рабочие/соединения/кэши. Проверь подписки на события, setInterval/setTimeout, открытые индексы и хранилища. Для каждого места укажи файл/строку, причину и как освободить.
```

### 2. Security / auth / sandbox

```text
Аудит: безопасность. Проверь хранение секретов и ключей (не должно быть в открытом виде), авторизацию и проверку прав, ограничения песочницы при выполнении кода, маскировку секретов в логах и экспортах. Перечисли найденные уязвимости с местом и риском.
```

### 3. Data integrity / persistence

```text
Аудит: целостность и персистентность. Проверь транзакции, согласованность состояния и хранилища, корректность записи/чтения, отсутствие гонок при сохранении. Для каждого нарушения укажи, как воспроизвести и как исправить.
```

### 4. Race conditions / lifecycle

```text
Аудит: гонки и жизненный цикл. Найди места, где доступ к общему состоянию идёт конкурентно без синхронизации (очереди, async-операции, события). Проверь корректность запуска/остановки, повторный запуск, уничтожение. Дай рецепт синхронизации для каждого случая.
```

### 5. Types / contracts / mismatches

```text
Аудит: типы и контракты. Проверь согласованность интерфейсов и их реализаций, соответствие типов на границах модулей, обработку неожиданных данных. Перечисли несовпадения контрактов с местами и предлагаемыми правками.
```

## Ритуал одного раунда

1. Выбери **одну** зону (один из пяти промтов).
2. Запусти аудит → получи список багов.
3. Расставь приоритеты CRITICAL/HIGH/MEDIUM/LOW.
4. На каждый CRITICAL/HIGH — напиши тест или чек-кейс.
5. Почини → прогони тесты → убедись, что зона стабилизировалась.
6. Зафиксируй версию и статус «зона прошла аудит».

## Как оценивать прогресс

- Прогресс — не «ноль багов», а **уменьшение доли критичных** и рост числа модулей со статусом «прошёл аудит».
- Если один и тот же класс багов возвращается после фиксов — это признак контрактной проблемы, а не точечной: исправляй на уровне контракта/модели мира.

## Работа с агентами

Копируй нужный промт (лучше несколько одним блоком) и вставляй в чат агента — opencode, z.ai и т.п. Агент прогонит аудит по конкретной зоне и вернёт локализованный список проблем. Это быстрее и чище, чем общий «найди баги».
